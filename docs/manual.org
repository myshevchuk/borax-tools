This manual describes what borax does with a file, every setting that
changes it, and the template language that decides what your files end
up being called. The [[file:../README.md][README]] is the short version: what the tool is for,
how to install it, and a handful of examples.

* What a run does

  ~resolve~, ~rename~, and ~bib~ turn a file into a record, and then do
  something with the record. They share the first half of that sentence
  and differ in the second.

  1. *Identify the file by its contents.* A file is hashed before it is
     opened, so borax knows which file it is looking at whatever the
     file is currently called.
  2. *Ask the library.* If the run's library tracks this path and these
     bytes, its linked item's record is the answer. borax does not open
     the file, extract anything, ask a service or either cache, compare
     titles, or update the content index for that file.
  3. *Otherwise, extract an identifier.* borax first asks the content
     index unless you used ~--no-cache~. On a miss, the cheap passes run
     and the first hit wins: the PDF's embedded metadata — the XMP
     packet, then the Info dictionary — and after that the page text
     layer, reading as many pages from the front as
     ~extraction.page-limit~ allows. What it is looking for is a DOI or
     an arXiv id.
  4. *Resolve that identifier to a record.* The enabled services are
     asked in turn — Crossref, OpenAlex, arXiv — through an on-disk
     response cache, and no faster than the pacing allows. What comes
     back is normalized into one record model, a superset of CSL-JSON.
  5. *Render a name, a citation key, or both.* The record's entry type
     chooses the template; the template renders a string; sanitization
     makes that string a legal file name on every supported platform.
  6. *Do the command's work.* ~resolve~ reports what it found and stops.
     ~bib~ writes bibliography output. ~rename~ plans a move for each
     file, then either asks about the move or handles it as part of a
     batch.

  The run's library is the nearest ~.borax.toml~ at or above the run's
  start directory, or the configured ~library-root~. borax reads its
  item and artifact stores once, before the first file. Every file is resolved
  against that start-of-run snapshot. An applying rename may record
  earlier files, but those writes do not become answers for later files
  in the same run.

  The library tracks a file when exactly one artifact record at the
  file's normalized path contains its content hash anywhere in its hash
  history, and that record links to an identity carried by exactly one
  item file. Relative paths and spellings that contain ~.~ or ~..~ are
  compared as the same path. Every history entry counts. This means
  restored older bytes resolve from the currently linked item, including
  bytes recorded before the artifact was re-linked to another item.
  A byte-identical copy at another path, or a file moved without
  ~borax reconcile~, is untracked and follows the ordinary resolution
  path.

  The library may fail to answer because records at the path do not hold
  these bytes, several records match, the matching record has no usable
  item, a recorded file cannot be hashed, or no readable record names
  the path and the artifact store could not be read completely. borax
  reports that problem with the file, then resolves it through the
  content index, extraction, services, and conflict check as if it were
  untracked. The problem is not itself a skip or finding and does not
  change the exit status.

  When a consulted artifact store could not be listed or contains
  unreadable records, borax writes at most one of these warnings on
  standard error:

  #+begin_example
    the library's artifact records could not be listed, so no file is resolved from the library; borax validate reports why
    1 artifact record could not be read, so a file it records is resolved as if the library did not track it; borax validate names it
    <n> artifact records could not be read, so a file one of them records is resolved as if the library did not track it; borax validate names them
  #+end_example

  The warning does not change the exit status.

  Three properties hold across all of it, and they are the reason the
  tool is shaped this way:

  - *It moves nothing without your decision.* By default on a terminal,
    ~borax rename~ asks before each move. In a batch, only ~--apply~
    authorizes the moves in the plan.
  - *It never overwrites.* A rendered name that is already taken is a
    collision, settled by the collision policy — a suffix, or a skip —
    and never by writing over what is there.
  - *It never guesses.* A file with no identifier, or an identifier no
    service knows, is skipped with the reason attached. borax does not
    infer a citation from a file name.

  Every subcommand emits the same typed event stream, rendered either
  as prose or, with ~--json~, as one JSON object per line. That stream
  is the integration contract, and it is what a run log holds.

  Human output closes with a line fitted to the command. A ~rename~ run
  uses a summary that counts each rename outcome separately:

  #+begin_example
    3 resolved, 1 renamed, 0 skipped, 12 already named
  #+end_example

  ~resolve~ and ~bib~ instead report resolution totals. Commands that
  produce their own report or totals line normally end there. JSON
  output and run logs still close with all seven ~run-finished~
  counters.

  A file that already carries the name its record implies is successful,
  not skipped. It does not cause the partial-success exit code, 2. A run
  over a library in which every file is already named exits 0.

* Commands

  Every command that works on files takes paths. A directory contributes
  every ~.pdf~ file below it, recursively and in sorted order; the
  extension is compared without regard to case. A file named directly is
  taken as it is, whatever it is called — including one that cannot be
  read, so that a mistyped name is reported rather than quietly dropped
  from the batch. A path named twice is worked on once.

** borax resolve

   #+begin_src sh
     borax resolve papers/
   #+end_src

   Resolves each file to a record and reports what was found, changing
   nothing on disk beyond the caches and the run log. This is the
   command to reach for when you want to know whether borax can identify
   a batch at all.

   Inside a library, ~resolve~ asks the library before the content
   index. A tracked file reports
   ~<path>: resolved <identifier> via <source> (from the library)~. If
   the library cannot answer, borax appends ~; the library could not
   answer: <what>~ to the ordinary resolution or skip line after the
   fallback. ~--no-cache~ still asks the library because the library is
   authoritative state, not a cache.

   It is the one command that resolves files concurrently, so it takes
   ~--concurrency~.

   Its human output ends with the resolved and skipped totals, including
   zeros:

   #+begin_example
     1 resolved, 0 skipped
   #+end_example

** borax rename

   #+begin_src sh
     borax rename papers/           # ask before each move
     borax rename --batch papers/   # preview the whole plan
     borax rename --apply papers/   # move the whole plan
   #+end_src

   Renames each file after the record resolved for it. A run is
   interactive when standard input is a terminal, output is human rather
   than ~--json~, ~--apply~ is absent, and ~rename.batch~ is ~false~.
   These are the defaults when you run the command from a terminal.

   Every other rename run is a batch. ~--batch~ selects a preview that
   reports each move as ~would rename to~ and changes no file.
   ~--apply~ selects a batch and moves every file its plan names, just as
   it did before interactive renaming was added. A redirected, piped,
   cron, or ~--json~ run is always a batch and never asks a question.
   A batch reports every file already carrying its rendered name as
   ~already named~.

   Use ~--no-batch~ to override a configured batch default when you want
   questions at a terminal. ~--apply --no-batch~ is a usage error naming
   both flags. It reads, resolves, and moves nothing, and exits with the
   fatal code, 1.

   ~rename~ is also where bibliography output and admission to a
   library happen. It accepts ~--bib~, ~--sidecars~, ~--duplicates~,
   ~--collision~ and ~--record~ alongside the resolution settings.
   An applying run inside a library writes an artifact record for each
   file it moves or finds already named, and links that record to an
   item for the resolved work. A preview writes neither kind of record.

   With recording enabled, duplicate checks use the library as the run
   has left it so far. Of two byte-identical files in one run, an
   applying run admits the first and a preview plans it; both report the
   second as a content duplicate. The same is true of two different
   files for one work: a batch skips the second, while an interactive
   run asks whether to file it as another artifact of the existing item.
   A file's own artifact record never makes it a duplicate of itself:
   borax passes over that record and keeps looking, so a genuine second
   copy recorded elsewhere in the library is still reported. Nor is a
   file a work duplicate of the item its own record already links to,
   so the several artifacts of one item never skip each other.
   ~--no-record~ disables both checks and writes no artifact record or
   item. It does not stop ~rename~ from asking the start-of-run library
   what a tracked file is. If moving a changed artifact without updating
   its record would strand that record, borax refuses the move and tells
   you to run ~borax reconcile --rehash~ first.

   It works one file at a time, so that a file's verdict and its fate
   stay adjacent in the stream. That is why it takes no
   ~--concurrency~.

*** The interactive session

    borax asks about every file whose outcome you can change: a file it
    can rename, one with no identifier, one whose identifier did not
    resolve, one with a title conflict, a second artifact of a work the
    library already holds, and an unreadable or encrypted file whose
    content hash is known. It also asks about an already-named file when
    you use ~--no-skip-named~. Before the question, borax shows the
    evidence it has on standard error:

    #+begin_example
      ── 3 of 17 ──────────────────────────────────────────────────────────
      file        50-Article Text-95-2-10-20240507.pdf
      identifier  doi:10.15407/bioorganica2023.01.010, from the text layer
      record      Crossref
      type        journal article
      title       Applications of chiral sulfinyl auxiliaries in the asymmetric
                  synthesis of fluorinated amines and amino acids
      authors     Nataliya V. Lyutenko, Alexander E. Sorochinsky, Vadim A.
                  Soloshonok
      issued      2023
      in          Ukrainica Bioorganica Acta 18(1), 10–21
      file says   nothing read
      new name    lyutenko2023_ApplicationsChiralSulfinyl.pdf
      ? What should happen to this file?
      > Rename
        Supply an identifier
        Skip
        Quit
      [↑↓ to move, enter to select]
    #+end_example

    The rule gives this file's position in the run. ~file~ names it as
    the run does: relative to where you started the run, or in full when
    it lies outside. ~identifier~ is the identifier borax looked up and
    says whether it came from embedded metadata or the text layer. It is
    kept on one line. For a library answer, it names the item's
    identifier without an origin clause because nothing was looked up.
    ~record~ names the service or services that supplied the record. It
    adds ~from an earlier run~ when the content index answered, and
    ~from the library~ when an item's provenance names services. If the
    item names no service, it reads ~the library~.

    When the library could not answer, a ~library~ line states the
    problem. It follows ~record~ for a resolved file and follows the
    reason lines for a file that did not resolve.

    A library-answered file gets the same move question as any other
    resolved file. Supplying another identifier re-identifies it and
    re-links its artifact as described under
    [[*Remembering your answer][Remembering your answer]]. An
    already-named tracked file is still passed over when
    ~rename.skip-named~ is on.

    ~type~, ~title~, ~authors~, ~issued~, and ~in~ come from the record.
    A field the record does not contain is omitted. The author line
    names up to three authors and counts any others. The issued date
    uses as much precision as the record contains. Other long values
    wrap under a hanging indent without being truncated.

    Everything the description quotes from a record or from a file's own
    metadata is written out rather than acted on, control characters
    included: a PDF's title is written by whoever made the file, and an
    escape sequence in one would otherwise be able to redraw the
    question you are answering.

    ~file says~ lists every title found in the file's XMP or document
    information, one per line — including one borax judged a producer's
    leftover rather than a title, since you are better placed to say
    which is the work's. It reads ~nothing read~ when there was nothing
    to read: the file carries no title of its own, or the content index
    or library answered and the file was never opened. ~new name~ is the
    name the file would take.

    The target includes a collision suffix when one is needed. A
    separate line below ~new name~ then names the rendered name that was
    already taken. When a template creates a subdirectory, the target
    also includes that subdirectory, such as ~sub/name.pdf~. ~Rename~ is
    selected first, so Enter accepts the move. The file is moved
    immediately and reported as ~renamed to <name>~, just as it is in an
    applying batch.

    Choose ~Skip~ to leave the file in place. If borax proposed a move
    from a record it accepted on its own, the skip reason is ~declined~.
    A file borax could not settle keeps that reason instead, such as ~no
    identifier found~ or a title conflict. The proposed name remains
    free, so if the next file produces the same name, borax offers that
    name without a suffix. A name is claimed only after you accept its
    move.

    The choices depend on what borax knows. The first choice is what
    Enter selects:

    | Situation                                        | Choices                                                     |
    |--------------------------------------------------+-------------------------------------------------------------|
    | A record produces a move                         | Rename; Supply an identifier; Skip; Quit                     |
    | No identifier was found                          | Supply an identifier; Skip; Quit                             |
    | No service holds the identifier                  | Supply an identifier; Skip; Quit                             |
    | Services could not give a usable answer          | Try the services again; Supply an identifier; Skip; Quit     |
    | A conflicting record produces a move             | Skip; Rename anyway, to =<name>=; Supply an identifier; Quit |
    | A conflicting record produces no move            | Skip; Supply an identifier; Quit                             |
    | The file is unreadable, but its hash is known    | Supply an identifier; Skip; Quit                             |
    | The file is already named under ~--no-skip-named~ | Keep this name; Supply an identifier; Quit                   |

    A title conflict shows the record's ~title~, the file's ~file
    says~ title, and their similarity on a ~conflict~ line. Skipping is
    the default. ~Rename anyway, to <name>~ names the target explicitly,
    so pressing Enter never overrides the conflict.

    A file with no identifier shows ~identifier  none found in the
    file~. If an identifier did not resolve, ~no record~ lists what each
    service answered. ~Try the services again~ appears only when the
    services were unavailable, rate-limited, or returned unusable data.
    It does not appear when every service confirmed that it did not hold
    the identifier. An unreadable file shows the error on an ~unreadable~
    line.

    *Supplying an identifier.* Choose ~Supply an identifier~ when you
    know what the file is but borax did not find the right identifier.
    borax prompts:

    #+begin_example
      ? Identifier — a DOI, an arXiv id, or pmid:/isbn: and the number
    #+end_example

    You can paste a DOI in any form borax extracts, including a
    ~https://doi.org/...~ URL. You can enter an old-style or new-style
    arXiv identifier, with or without the ~arXiv:~ prefix. A PMID or
    ISBN must begin with ~pmid:~ or ~isbn:~. borax refuses bare digits
    because they can be either a PMID or an ISBN.

    If the input contains no accepted identifier, borax names the
    accepted forms and asks again without contacting a service. An
    empty line, Esc, or Ctrl-C abandons the input and returns to the
    file's menu without changing it.

    borax looks up an accepted identifier through the usual services.
    If it resolves and produces a move, borax shows the record and asks
    about that move. If it does not resolve or produces no move, borax
    reports what happened and returns to the file's own menu. A file
    that already had a usable record keeps it while you try other
    identifiers.

    borax compares the file's titles with a supplied record. If they
    disagree, it shows both titles and their similarity. You may then
    skip, accept the record with ~Rename anyway, to <name>~, or supply
    another identifier. This check can catch a mistyped identifier that
    resolves to an unrelated work.

    Supplying an identifier does not make borax search by title. You
    must provide the identifier yourself.

    *Remembering your answer.* After you rename a file from a supplied
    identifier or by accepting a title conflict, borax stores the record
    under the file's content hash in the content index. A later
    interactive or batch run can use that record without extraction, a
    service lookup, a conflict check, or another question.

    Inside a library, the applying rename also links the artifact record
    to the item for the accepted record. Supplying a different identifier
    for a tracked file re-identifies the file and re-links that artifact.
    A later run resolves the tracked file from the linked item before it
    asks the content index. ~borax cache --clear~ and ~--no-cache~ do not
    remove or bypass that library answer.

    borax writes this entry only when you accept the rename. Supplying
    an identifier and then skipping stores no candidate record and
    produces no sidecar or master-bibliography entry for that candidate.
    A record the content index already held for the file remains there.

    This memory is best-effort. If the content index cannot be written,
    or borax falls back to an in-memory cache, a later run asks again.
    ~borax cache --clear~ removes stored answers. ~--no-cache~ bypasses
    the read but still writes the accepted answer.

    By default, an interactive run passes over a file that already
    carries its rendered name without showing its resolution, outcome,
    or a question. The summary still accounts for it:

    #+begin_example
      12 resolved, 0 renamed, 0 skipped, 12 already named (not shown)
    #+end_example

    If the run hides only some already-named files, the clause gives the
    number, for example ~12 already named (4 not shown)~. Use
    ~--no-skip-named~ to show these files and choose ~Keep this name~,
    ~Supply an identifier~, or ~Quit~. Keeping the name is the default.
    This setting changes only an interactive run; a batch always reports
    every file and asks nothing.

    Passing over a file changes only what the terminal shows. The JSONL
    event stream and run log still contain all of its events.
    Bibliography output is also still shown, including a sidecar written
    beside the file, a master ~.bib~ merge, or a failure to write either.

    borax reports without a question when no answer can lead to a move.
    This includes a duplicate, a file whose content hash is unknown, a
    target taken under the ~skip~ collision policy, and a record that
    renders no name. A resolved file whose proposal is not a move is also
    reported without a question, except for an already-named file shown
    under ~--no-skip-named~.

    At a file's menu, choose ~Quit~, press Ctrl-C, or press Esc to end
    the session. The file at that question and every later file stay
    untouched and are not resolved. Work already completed remains in
    place. The summary counts the remainder as not reached:

    #+begin_example
      3 resolved, 1 renamed, 3 skipped, 2 not reached
    #+end_example

    A run with any file not reached exits with the partial-success code,
    2, as does a run with skipped files.

** borax bib

   #+begin_src sh
     borax bib --bib library.bib papers/
   #+end_src

   Writes bibliography output for each file — entries merged into a
   master ~.bib~, sidecars beside the files, or both — and renames
   nothing. It renders citation keys but no file names, so a
   ~templates.default~ that will not compile does not stop it.

   Inside a library, ~bib~ asks the library before the content index.
   A tracked file is cited from its linked item's record, so a correction
   made directly to that item appears in the bibliography without a
   service query.

   ~bib~ takes files as input. An item with no artifact has no file for
   this command to resolve, so it produces no bibliography entry.

   Its closing line reports the resolved and skipped totals, including
   zeros, and adds the unmatched lookup count when it is nonzero. It
   does not report a renamed or already-named count.

** borax config

   #+begin_src sh
     borax config
     borax config --mailto you@example.org
   #+end_src

   Prints every setting, its effective value, and the layer it came
   from:

   #+begin_example
     bib.duplicates = "skip"  # defaults
     mailto = "you@example.org"  # global /home/you/.config/borax/config.toml
     rename.collision = "skip"  # override /home/you/papers/.borax.toml
   #+end_example

   It accepts every setting flag, because an override passed to it is
   the question it answers rather than a no-op: it reports what *this
   invocation* would resolve to. It compiles no templates, so it keeps
   working on a configuration no other command will accept — which is
   the situation you most want it in.

** borax cache

   #+begin_src sh
     borax cache
     borax cache --clear
   #+end_src

   Reports what the on-disk response cache holds, or empties it.

   The four library commands below each accept
   ~--run-log~/~--no-run-log~ and ~--json~. ~--identify~ and ~--rehash~
   select work for one invocation; they are not configuration keys and
   have no ~--no-~ forms.

** borax status

   #+begin_src sh
     borax status [PATH]
     borax status --identify [PATH]
   #+end_src

   Reports how many artifacts, items, artifact records, and orphans a
   library holds. An /artifact/ is a PDF owned by the library tree,
   outside ~.borax/~, ~items/~, and any nested library. An /orphan/ is
   an artifact whose path no artifact record names. A record whose path
   holds no file is missing, not orphaned.

   Without ~--identify~, the command opens no document. It writes no
   library state with or without the flag. It also works on an unmarked
   directory, treating that directory as the root for this report. If
   you omit ~PATH~, the working directory is used.

   ~--identify~ opens every surveyed artifact, tracked or not, and runs
   the same extraction passes as ~resolve~. It queries no service and
   writes one result per artifact in survey order. ~status~ also accepts
   ~--page-limit~ for this extraction.

   A successful result names the identifier and the pass that found it.
   A failed result distinguishes a missing text layer, readable text
   without an identifier, an encrypted document, and an unreadable
   file:

   #+begin_example
     <path>: identifier <identifier> from embedded metadata
     <path>: identifier <identifier> from the text layer
     <path>: identifier <identifier> from the file
     <path>: no identifier found; the pages read hold no text
     <path>: no identifier found in its metadata or the pages read
     <path>: encrypted, so no identifier could be read
     <path>: unreadable (<message>)
   #+end_example

   Each ~<path>~ is library-relative and uses ~/~ as its separator.
   Control characters in a path, identifier, or reader message appear
   as ~\xNN~ rather than reaching the terminal. A metadata title counts
   only when the metadata pass finds an identifier in it.

   The report's ~identifiable~ total counts the artifacts whose result
   names an identifier. It does not mean that a service recognised the
   identifier. A failed extraction is neither a skip nor a finding and
   does not change the exit status.

   A nested directory with its own ~.borax.toml~ is another library.
   ~status~ excludes its entire subtree from the parent counts and lists
   it as a nested library.

   With ~--identify~, the per-artifact lines precede the library report.
   Human output ends with that report, with or without the flag. It does
   not add a resolved, renamed, and skipped summary.

** borax validate

   #+begin_src sh
     borax validate [PATH]
   #+end_src

   Checks the library's item and artifact records and repairs nothing.
   It reports a dangling item link, a duplicate identity, a store file
   whose name disagrees with the identity inside it, a path that is not
   library-relative, an empty hash history, a malformed hash, a history
   entry without a run, a store file that cannot be read, or an existing
   ~items/~ or ~.borax/artifacts/~ directory that cannot be listed. An
   unlistable directory is an ~unreadable~ finding; a missing directory
   remains an empty store.

   Orphans, missing artifacts, and items no artifact record links to are
   counts rather than findings. They are valid library states. The
   command exits with the partial-success code, 2, when it reports a
   finding, and exits 0 when it reports none.

   Each finding has its own line. Human output ends with the validation
   totals, including the findings count, and does not repeat that count
   in another summary line.

** borax reconcile

   #+begin_src sh
     borax reconcile [PATH]
     borax reconcile --rehash [PATH]
   #+end_src

   Repairs artifact records after files have been moved or edited
   outside borax. It first trusts a matching recorded size and
   modification time. ~--rehash~ hashes every artifact instead, which
   also catches a same-size in-place edit within the filesystem's
   modification-time granularity.

   Reconciliation completes four steps in order across the library. It
   first settles records whose own paths still hold their artifacts.
   It then repairs stale paths by matching any hash in each record's
   history, preferring the current hash. Next it treats an unmatched
   file at a record's own path as an in-place edit and appends its new
   hash. Finally, it leaves unresolved records unchanged.

   A record with more than one candidate is ambiguous, and so is a
   file two records both match. borax reports every candidate and
   changes nothing rather than guessing. It creates no record for an
   orphan and deletes no record. A pass over an untouched library writes
   no store file.

** borax adopt

   #+begin_src sh
     borax adopt [PATH]
   #+end_src

   Records orphans from facts borax already knows locally. For each
   orphan, it hashes the file and asks the content index, the local cache
   of records borax resolved before. When the index answers, borax writes
   an artifact record and links it to an existing item or creates an
   item. It queries no service, opens no document, and moves, renames,
   and deletes nothing.

   An unknown orphan stays an orphan. An orphan whose bytes already
   occur in an artifact record's hash history also stays an orphan and
   is reported as held by that record. It may be a recorded artifact
   moved outside borax, in which case run ~reconcile~, or a copy. Running
   ~adopt~ again does not change records it already wrote. After ~borax
   cache --clear~, the content index is empty, so adoption records
   nothing and still succeeds.

   ~adopt~ neither reads citation sidecars nor the retired
   ~.borax/ledger.jsonl~. It refuses to run outside a library established
   by ~.borax.toml~ or ~library-root~, because it has nowhere to write
   library state.

** Choosing how to record existing files

   Use ~adopt~ when borax resolved the same bytes on an earlier run and
   you want an offline operation that cannot rename anything. Use
   ~rename --apply~ when an orphan is unknown to the content index: it
   can extract an identifier, query services, rename the file under the
   current templates, and record it. Use ~reconcile~ when a record
   already exists but its artifact was moved or edited outside borax.

* Settings

** Where a setting can be set

   A setting can come from four places. They are consulted lowest
   first, and a later one wins for the keys it names:

   1. The built-in defaults.
   2. The global configuration file: ~borax/config.toml~ under your
      configuration directory — ~$XDG_CONFIG_HOME~, else ~$HOME/.config~;
      on Windows ~%APPDATA%~, else ~$XDG_CONFIG_HOME~.
   3. The nearest ~.borax.toml~ at or above the file being worked on.
      Directories are tried from the file's own directory upward, and
      the first hit wins, so no more than one override file applies to
      any file — and an invocation spanning two trees applies each
      tree's overrides to its own files.
   4. The environment, as ~BORAX_<KEY>~ with the key uppercased and
      every ~.~ and ~-~ turned into ~_~; so ~network.min-interval-ms~ is
      ~BORAX_NETWORK_MIN_INTERVAL_MS~.
   5. The command line.

   Merging is per key, not per layer. A ~.borax.toml~ that sets only
   the collision policy leaves every other setting to the layers below
   it, and a ~[templates]~ table that defines only ~thesis~ keeps the
   ~default~ it inherits. ~borax config~ names the layer each value
   actually came from, which is how you settle an argument about which
   file is in charge.

   A /library/ root is the configured ~library-root~, or otherwise the
   nearest ancestor with a ~.borax.toml~. Its ~.borax/~ holds the
   artifact records and run logs, while ~items/~ under the root holds the
   item store. A nested marker begins another library, and the outer
   library stops at that boundary. The boundary is lexical: symlinks are
   not followed, and a symlink is neither an artifact nor an orphan.

   A library keeps two authoritative text stores. An item is a logical,
   independently citable work. It lives at
   ~items/<key>.<uuid>.toml~, where ~<key>~ is the citation key when the
   item is created and is only a label; borax never renames the file
   when the key later changes. The ~id~ field inside the file is the
   item's identity. An item may have no artifact, and several artifacts
   may link to one item.

   An artifact record describes one physical file. It lives at
   ~.borax/artifacts/<uuid>.toml~ and records its own identity, its item
   link, its last-known library-relative path, its size and modification
   time, and its hash history. Each hash entry names the run, timestamp,
   and borax version that recorded it. A citation sidecar is optional
   derived output, not a library record: borax reads neither a sidecar
   nor a retired ledger file to reconstruct the library.

** The settings

   | Key                       | Flag                             | Default   |
   |---------------------------+----------------------------------+-----------|
   | ~bib.duplicates~          | ~--duplicates~                   | ~skip~    |
   | ~bib.path~                | ~--bib~                          | unset     |
   | ~bib.sidecars~            | ~--sidecars~/~--no-sidecars~     | ~false~   |
   | ~library-root~            | none                             | unset     |
   | ~extraction.page-limit~   | ~--page-limit~                   | ~3~       |
   | ~record~                  | ~--record~/~--no-record~         | ~true~    |
   | ~mailto~                  | ~--mailto~                       | unset     |
   | ~network.cache~           | ~--cache~/~--no-cache~           | ~true~    |
   | ~network.concurrency~     | ~--concurrency~                  | ~4~       |
   | ~network.min-interval-ms~ | ~--min-interval-ms~              | ~100~     |
   | ~rename.batch~            | ~--batch~/~--no-batch~           | ~false~   |
   | ~rename.collision~        | ~--collision~                    | ~suffix~  |
   | ~rename.skip-named~       | ~--skip-named~/~--no-skip-named~ | ~true~    |
   | ~run-log~                 | ~--run-log~/~--no-run-log~       | ~true~    |
   | ~sources~                 | ~--sources~                      | all three |

   - ~bib.duplicates~ :: What to do with an entry already in the master
     ~.bib~: ~skip~ or ~update~.
   - ~bib.path~ :: The master ~.bib~ file entries are merged into.
   - ~bib.sidecars~ :: Write a sidecar record beside each resolved file.
   - ~library-root~ :: The directory anchoring the library. Set, it
     replaces the search for a ~.borax.toml~ outright, which is how an
     unusual layout puts its state somewhere no override file sits.
   - ~extraction.page-limit~ :: How many pages from the front the text
     pass reads. Zero disables the text pass. The default of three
     covers the usual case: publishers put the DOI on the first page,
     and a cover sheet rarely pushes it past the third.
   - ~record~ :: Whether ~rename~ checks the library's artifact records
     for content and work duplicates, and whether an applying run writes
     artifact records and items. With it off, no duplicate check or
     store write is made. It does not disable reading the library before
     resolution. The safety check that prevents a move from stranding an
     existing record still runs.
   - ~mailto~ :: The contact address sent to the polite pools. Setting
     it is how you get the better rate limits, and it is good manners.
   - ~network.cache~ :: Whether resolving reads and writes the on-disk
     response cache. Turning it off also bypasses the content index, but
     it does not bypass a library item because the library is not a
     cache.
   - ~network.concurrency~ :: How many files ~resolve~ may work on at
     once.
   - ~network.min-interval-ms~ :: The floor on the gap between two
     requests to one service.
   - ~rename.batch~ :: Whether a terminal rename reports the whole plan
     instead of asking about each move. It is ~false~ by default. The
     flag pair is available on ~rename~ and ~config~ only. Unlike a
     per-file template or collision policy, this setting comes from the
     run's own configuration: the configuration found from the working
     directory where you start borax. A ~.borax.toml~ under an input
     directory does not change the mode of a run started outside it.
     Run ~borax config~ inside that directory to see its value and
     origin there. The setting does not authorize a move. An ~apply =
     true~ key in a configuration file remains a load-time error.
   - ~rename.collision~ :: What to do when two files want one name:
     ~suffix~ or ~skip~.
   - ~rename.skip-named~ :: Whether an interactive rename passes over
     files that already carry their rendered names. It is ~true~ by
     default. The flag pair is available on ~rename~ and ~config~ only.
     ~--no-skip-named~ shows these files, but does not ask about them.
     This setting does not affect a batch run.
   - ~run-log~ :: Whether a run writes its event stream to a log. An
     applying rename writes one regardless; see [[*Run logs][Run logs]].
   - ~sources~ :: Which services may be asked, comma-separated:
     ~crossref~, ~openalex~, ~arxiv~.

   Three tables have no flags at all — ~[templates]~, ~[citation-keys]~
   and ~[tables]~ — because their keys are open-ended. They are
   configuration-file-only, without exception.

** Settings on the command line

   A setting flag goes *after* the subcommand that reads it:

   #+begin_example
     borax rename --mailto you@example.org --apply papers/
   #+end_example

   ~borax --mailto you@example.org rename papers/~ is refused as an
   unknown argument. ~git commit -m~ and ~cargo build --release~ put
   their flags after the subcommand too.

   A subcommand accepts only the settings it can act on, so ~borax bib
   --help~ describes what ~bib~ does rather than everything borax can
   be configured to do. Naming a setting a command cannot act on is a
   usage error rather than a silent no-op.

   ~borax cache --no-cache~ was never going to make ~borax cache~ stop
   reading the cache; that flag decides whether /resolving/ consults
   it. ~borax rename --concurrency 8~ was never going to resolve eight
   files at once. Both are refused rather than accepted and dropped.

   ~--json~ is the exception: it goes on either side. It chooses how to
   render the event stream, and every subcommand honours it, so
   ~borax --json bib papers/~ and ~borax bib --json papers/~ are the
   same invocation.

   None of this limits what a configuration file may say. A
   ~.borax.toml~ sets every key regardless of which command runs, and
   so does an environment variable; neither is an argument to an
   invocation. So ~network.concurrency~ set in a file is reported by
   ~borax config~ and refuses nothing on a ~rename~ that will not read
   it.

   Every configurable boolean is offered as a pair of flags —
   ~--cache~/~--no-cache~, ~--sidecars~/~--no-sidecars~,
   ~--record~/~--no-record~, ~--batch~/~--no-batch~,
   ~--skip-named~/~--no-skip-named~, and
   ~--run-log~/~--no-run-log~ — which is how a flag that takes no
   value says all three things: on, off, and silent. Naming both halves
   of a pair is a parse error rather than a last-one-wins guess.

* The template language

  Once borax has resolved a file's metadata, it still has to decide
  what to call the file. You are the one who knows what your library
  should look like — one person wants ~smith2024_AwesomePaperBorax.pdf~,
  the next wants everything sorted into a directory per year. A
  /template/ is how you say which. It is a short string that borax
  renders once per file, using the record it resolved, to produce the
  new file name.

  With no configuration at all, borax uses this template:

  #+begin_example
    [auth:lower][year]_[shorttitle3:camel]
  #+end_example

  Rendered against a 2024 paper by Smith, Doe, and Roe titled "An
  Awesome Paper on Borax", it produces:

  #+begin_example
    smith2024_AwesomePaperBorax
  #+end_example

  The extension is not part of the template; borax keeps the original
  file's extension.

** Literal text and tokens

   A template is literal text with /tokens/ embedded in it. Anything
   outside a bracket is copied through verbatim — the ~_~ in the
   default template above is literal, and so are spaces, hyphens, and
   any other character you type. A token is a field name in square
   brackets, optionally followed by filters:

   #+begin_example
     [field]
     [field:filter]
     [field:filter:filter]
   #+end_example

   The field supplies a value from the record, and each filter
   transforms whatever the filter to its left produced. So
   ~[title:slug:trunc10]~ slugifies the title first and then cuts the
   slug to ten characters, which on our example record gives
   ~an-awesome~. Reversing the two filters would truncate first and
   slugify the shorter string, which is a different result.

   A field whose value the record does not have renders as the empty
   string. It is not an error, and it does not stop the run — see
   [[*Alternatives][Alternatives]] for how to supply a fallback.

   Do *not* expect to write a literal ~[~ in a template. There is no
   escape for it: ~[~ always opens a token. A ~]~ outside a token is
   literal.

** Fields

   | Field         | Value                                                                   | Example output                    |
   |---------------+-------------------------------------------------------------------------+-----------------------------------|
   | ~auth~        | The first author's family name.                                         | ~Smith~                           |
   | ~authors~     | Every author's family name, joined with ~-~.                            | ~Smith-Doe-Roe~                   |
   | ~authorsN~    | The first N family names; ~-etal~ is appended when that dropped anyone. | ~[authors2]~ → ~Smith-Doe-etal~   |
   | ~year~        | The year the work was issued.                                           | ~2024~                            |
   | ~title~       | The title, verbatim.                                                    | ~An Awesome Paper on Borax~       |
   | ~shorttitle~  | The first three words of the title that are not function words.         | ~Awesome Paper Borax~             |
   | ~shorttitleN~ | The same, keeping N words instead of three.                             | ~[shorttitle2]~ → ~Awesome Paper~ |
   | ~journal~     | The container title, verbatim.                                          | ~J. Chem. Ed.~                    |
   | ~volume~      | The volume the work appeared in.                                        | ~146~                             |
   | ~issue~       | The issue within that volume.                                           | ~12~                              |
   | ~pages~       | The page range, exactly as the record holds it.                         | ~1234-1245~                       |
   | ~firstpage~   | The first page of that range.                                           | ~1234~                            |
   | ~publisher~   | The publisher's name.                                                   | ~American Chemical Society~       |
   | ~doi~         | The normalized DOI.                                                     | ~10.1021/jacs.4c01234~            |
   | ~arxiv~       | The arXiv id, with any version suffix removed.                          | ~2401.12345~                      |
   | ~sha1~        | The hash of the file's contents, in lowercase hex.                      | ~da39a3ee5e…~                     |
   | ~entrytype~   | The record's CSL type string.                                           | ~article-journal~                 |

   A /function word/ is one of the sixteen words that carry no subject
   matter of their own — ~a~, ~an~, ~the~, ~of~, ~on~, ~in~, ~for~,
   ~and~, ~or~, ~to~, ~with~, ~at~, ~by~, ~from~, ~into~, ~upon~ —
   compared without regard to case. ~shorttitle~ skips them, which is
   why ~shorttitle3~ of "An Awesome Paper on Borax" is ~Awesome Paper
   Borax~ and not ~An Awesome Paper~.

   ~firstpage~ is the part of ~pages~ before the first dash — of any
   width, so ~-~, ~–~ and ~—~ all end it — with the surrounding
   whitespace trimmed. A value with no dash in it is its own first
   page, which is what keeps an article number whole: ~e0123456~ and
   ~045301~ come through unchanged, and a journal that cites by article
   number rather than by page gets what it wants from the same field.

   The ~entrytype~ field renders the CSL-JSON type string, which is not
   always the name you use to configure a template for that type. A
   journal article renders as ~article-journal~ here, but is configured
   under the key ~article~; a preprint renders as ~article~. See
   [[*Configuring templates][Configuring templates]].

** Filters

   | Filter                           | Effect                                                                                                                                      | Example                                                              |
   |----------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------+----------------------------------------------------------------------|
   | ~lower~                          | Lowercases the whole string.                                                                                                                | ~Smith~ → ~smith~                                                    |
   | ~upper~                          | Uppercases the whole string.                                                                                                                | ~Smith~ → ~SMITH~                                                    |
   | ~capitalize~                     | Uppercases the first character, lowercases the rest.                                                                                        | ~an AWESOME paper~ → ~An awesome paper~                              |
   | ~titlecase~                      | Uppercases the first character of each word, lowercases the rest, and keeps the spaces.                                                     | ~an awesome paper on borax~ → ~An Awesome Paper On Borax~            |
   | ~camel~                          | Title-cases, then removes the spaces.                                                                                                       | ~An Awesome Paper on Borax~ → ~AnAwesomePaperOnBorax~                |
   | ~slug~                           | Transliterates, lowercases, and replaces every run of characters outside ~a-z0-9~ with a single ~-~, trimming leading and trailing hyphens. | ~An Awesome Paper on Borax~ → ~an-awesome-paper-on-borax~            |
   | ~abbr~                           | Keeps the first character of each word, preserving case.                                                                                    | ~J. Chem. Ed.~ → ~JCE~                                               |
   | ~truncN~                         | Keeps the first N characters.                                                                                                               | ~[title:trunc11]~ → ~An Awesome ~                                    |
   | ~transliterate~                  | Folds common Latin letters to ASCII: ~ä~→~ae~, ~ß~→~ss~, ~ø~→~o~, ~ñ~→~n~, and the accented vowels lose their accents.                      | ~Müller~ → ~Mueller~                                                 |
   | ~regex("pattern","replacement")~ | Replaces every match of the pattern. ~$1~ refers to a capture group.                                                                        | ~[title:regex("[Bb]orax","B2O3"):slug]~ → ~an-awesome-paper-on-b2o3~ |
   | ~prefix("text")~                 | Puts the text in front of the value, and leaves the empty string alone.                                                                     | ~[volume:prefix("-")]~ → ~-146~                                      |
   | ~suffix("text")~                 | Puts the text after the value, and leaves the empty string alone.                                                                           | ~[auth:suffix("-")]~ → ~Smith-~                                      |
   | ~lookup("table")~                | Replaces the value with what the named external table holds for it.                                                                         | ~[journal:lookup("jcode")]~ → ~JACS~                                 |

   ~transliterate~ folds the Latin letters it knows and passes every
   other character through unchanged, so its result is not guaranteed
   to be ASCII; Greek, Cyrillic, and CJK survive it intact. Follow it
   with ~slug~ when you need a name that is certainly ASCII.

   ~truncN~ counts characters, not bytes, so it will not cut a
   multi-byte character in half.

   That ~prefix~ and ~suffix~ leave the empty string alone is the whole
   point of them: it lets a separator belong to the segment it
   separates, so a token that renders nothing takes its separator with
   it. Write

   #+begin_example
     [year]-[journal:abbr][volume:prefix("-")]-[firstpage]
   #+end_example

   and a paper in volume 146 is named ~2024-JCE-146-1234~, while one
   whose record has no volume is named ~2024-JCE-1234~ — not
   ~2024-JCE--1234~, which is what you would get from the more obvious
   ~-[volume]~.

   ~lookup~ is the one filter that consults something outside the
   record. It is documented under [[*External tables][External tables]].

** Alternatives

   Records are incomplete in different ways: a preprint has no DOI, an
   old scan has no arXiv id. Rather than fail, a token can list
   alternatives separated by ~||~, and the first one that renders
   something non-empty wins:

   #+begin_example
     [doi:slug || sha1:trunc8]
   #+end_example

   For a record that has a DOI, that renders ~10-1021-jacs-4c01234~.
   For one that does not, it falls back to the first eight characters
   of the file hash, ~da39a3ee~. Each alternative is a full
   field-and-filters chain of its own, and the filters run before the
   emptiness test, so an alternative that filters down to nothing is
   passed over.

   Whitespace around ~||~ is ignored. Elsewhere inside a token it is an
   error, so write ~[title:slug]~, never ~[title : slug]~.

** Filing into subdirectories

   A ~/~ in the rendered name is a directory separator, on every
   platform. That makes a filing scheme a matter of writing one into
   the template:

   #+begin_example
     [year]/[auth:lower][year]_[shorttitle2:camel]
   #+end_example

   renders ~2024/smith2024_AwesomePaper~, and borax creates the ~2024~
   directory if it is not already there.

   Inside a library, the rendered path is relative to the library
   root. This is the directory holding the ~.borax.toml~ that supplied
   the run's configuration, or the directory selected by the
   ~library-root~ setting. A template such as
   ~[journal]/[auth][year]~ therefore files a paper into ~Nature/~
   wherever the PDF currently sits in the library. Re-running over
   the library changes nothing. If the journal later renders as
   ~Science~, borax moves the file across into ~Science/~ rather than
   deeper into ~Nature/Science/~.

   When a run has no library root, a rendered subdirectory is
   relative to the file's current directory, as before. Such a run is
   not idempotent when the template contains a subdirectory. In either
   case, a rendered name containing no ~/~ renames the file where it
   already sits.

   Collisions are checked in the directory where the files will land,
   across every file the run sends there and in both preview and applying
   runs. Under the ~suffix~ policy, reaching the file's own current name
   means it is already named; borax never proposes a move onto that same
   name.

** Sanitization

   Every rendered name goes through a sanitization pass before it
   reaches the filesystem. You cannot turn it off, and templates cannot
   opt out of it. It applies the strictest rules of any supported
   platform — Windows's — everywhere, so that a library stays valid
   when it syncs between machines:

   - The characters Windows forbids (~<~ ~>~ ~:~ ~"~ ~\~ ~|~ ~?~ ~*~
     and the control characters) each become ~_~.
   - Trailing dots and spaces are trimmed.
   - A component whose name is a reserved Windows device (~CON~, ~PRN~,
     ~AUX~, ~NUL~, ~COM1~–~COM9~, ~LPT1~–~LPT9~) gets a ~_~ appended to
     its stem, so ~CON.pdf~ becomes ~CON_.pdf~.
   - A component longer than 255 bytes is truncated, keeping its
     extension; a whole path longer than 1024 bytes is trimmed until it
     fits.

   So a template that renders ~CON: a study? of borax.pdf~ is written
   to disk as:

   #+begin_example
     CON_ a study_ of borax.pdf
   #+end_example

   Sanitization applies per path component, so the ~/~ separators you
   wrote survive it.

** Configuring templates

   Templates live in the ~[templates]~ table of a configuration file:
   the global ~borax/config.toml~, or a ~.borax.toml~ in a directory of
   files, which overrides the global one for the files below it.
   Templates can only be set in these files — unlike the other
   settings, they cannot be set from an environment variable or a
   command-line flag, because their keys are open-ended.

   The ~default~ key is required and is what borax falls back to; every
   other key names an entry type and overrides the default for records
   of that type:

   #+begin_src toml
     [templates]
     default = "[auth:lower][year]_[shorttitle3:camel]"
     thesis  = "[auth:lower][year]_thesis"
     book    = "[year]/[authors2:slug]_[shorttitle:camel]"
   #+end_src

   The entry types you may use as keys are ~article~, ~preprint~,
   ~book~, ~chapter~, ~thesis~, ~report~, ~patent~, and ~standard~.
   These are borax's own names, not the CSL-JSON strings the records
   serialize to, because a configuration file is written by a person
   and ~[templates.article]~ should mean what a person means by it. The
   CSL strings differ in exactly the confusing place: CSL calls a
   journal article ~article-journal~ and a preprint ~article~.

   Merging is per key, not per file, so a ~.borax.toml~ that sets only
   ~templates.thesis~ keeps the ~default~ it inherits from the global
   file.

** Citation keys

   When borax writes bibliography output — the master ~.bib~ file, or a
   sidecar beside a file — each record needs a /citation key/, the name
   you type into a ~\cite{...}~. Keys come from templates too, but from
   a table of their own, ~[citation-keys]~, because the two settings
   have no reason to move together: you may want long, sortable file
   names and short keys. Changing how your files are named never
   changes how your works are cited.

   The table has the same shape as ~[templates]~, uses the same
   template language, and is merged the same way. With no
   configuration, the key template is:

   #+begin_example
     [auth:lower][year]
   #+end_example

   so the 2024 paper by Smith renders the key ~smith2024~, whatever
   ~templates.default~ happens to be. A record whose key would collide
   with one already in the master file gets a deterministic ~a~, ~b~,
   ~c~ suffix — ~smith2024a~ — and a record too sparse to render any
   key at all is reported as uncitable rather than given a made-up one.

   Override the default, or any entry type, the way you would a
   file-name template:

   #+begin_src toml
     [citation-keys]
     default = "[auth:lower][year]"
     thesis  = "[auth:lower][year]phd"
   #+end_src

   A rendered key is stripped of whitespace and of the four characters
   a BibTeX key cannot carry (~,~, ~{~, ~}~, ~%~), so a template that
   renders ~Smith, J. 2024~ yields the key ~SmithJ.2024~.

* External tables

  Some of what a name should carry is not in the record and never will
  be. The short code you cite a journal by — ~JACS~ for the Journal of
  the American Chemical Society — is a decision somebody made, not a
  fact Crossref reports. If you keep a bibliography, you probably
  already have that decision written down in a file somewhere,
  maintained by hand and read by whatever other tools you use. An
  /external table/ is how borax reads that same file, so there is one
  copy of it rather than two.

  A table is a tab-separated file with a header row. One column
  supplies the keys, another supplies the values, and a template asks
  the table what it holds for a value it has. That is all a table can
  do: it substitutes one string for another. Nothing in it executes,
  nothing it holds can fail at render time, and a run over the same
  files with the same table always produces the same names.

** Declaring a table

   Declare one in the ~[tables]~ table of a configuration file, beside
   ~[templates]~ and ~[citation-keys]~:

   #+begin_src toml
     [tables.jcode]
     path  = "journal_titles.tsv"
     key   = "title"
     value = "abbreviation"
   #+end_src

   and reach it from a template with the ~lookup~ filter, naming the
   table you declared:

   #+begin_example
     [year]-[journal:lookup("jcode")]-[firstpage]
   #+end_example

   Given a file whose columns are separated by tabs and whose header
   names them:

   #+begin_example
     abbreviation    title                                       shorttitle
     AA              Amino Acids                                 Amino Acids
     JACS            Journal of the American Chemical Society    J. Am. Chem. Soc.
   #+end_example

   a 2024 paper in that journal on pages 1234–1245 is named
   ~2024-JACS-1234~.

   Columns are named rather than positional. ~key~ and ~value~ say
   which column means what, and a column the declaration does not name
   is ignored — so the layout of the file is nobody's business but its
   own, and the same curated file can serve several tools, each naming
   the columns it needs. borax defines no format of its own here and
   asks the file for no column it does not already have.

   ~key~ may also name several columns:

   #+begin_src toml
     key = ["title", "shorttitle"]
   #+end_src

   and then a row is reachable by either spelling of its journal. A row
   whose two cells happen to be identical — ~Amino Acids~ is both the
   title and the short title, and a curated file really does have such
   rows — contributes one key, and is not something borax complains
   about.

** What matches what

   Both sides of a lookup are folded before they are compared: every
   key a table supplies, and every value flowing into the filter. The
   fold is these four steps, in this order and no others:

   1. Transliterate, by the table the ~transliterate~ filter uses:
      ~ä~→~ae~, ~ö~→~oe~, ~ü~→~ue~, ~ß~→~ss~ and their uppercase
      forms; ~æ~→~ae~, ~ø~→~o~, ~å~→~a~, ~đ~→~d~, ~ł~→~l~, ~ñ~→~n~,
      ~ç~→~c~; and the accented vowels lose their accents. A character
      the table does not name passes through unchanged.
   2. Lowercase, by Unicode default case conversion.
   3. Replace every maximal run of characters outside ~a-z0-9~ with a
      single ~-~.
   4. Trim the leading and trailing ~-~.

   That is exactly what the ~slug~ filter does, and the two are one
   definition rather than two that agree today. So ~J Am Chem Soc~
   finds the row keyed ~J. Am. Chem. Soc.~, and a container title with
   a trailing period finds the row written without one. This is what
   makes the feature usable at all: the sources disagree about a
   journal's punctuation far more often than they disagree about its
   words. ~Zeitschrift für Chemie~ folds to ~zeitschrift-fuer-chemie~.

   The steps are spelled out here because they are a contract and not
   an implementation detail. Another program reading the same file has
   to fold the same way, or the two of you will resolve the same
   journal to different rows. Step 1 in particular is a choice rather
   than a standard: borax expands ~ä~ to ~ae~ in the German manner,
   where Unicode's own normalization would strip the diaeresis and
   leave ~a~.

   A string that folds to nothing is not a key. A row whose key cell
   folds away — a title written entirely in a script step 1 does not
   cover — is dropped, with a warning naming the file and the line, and
   a value that folds away matches no row at all. The alternative would
   be worse than a miss: every such title would match every other one.

   Two rows that fold to the same key but hold different values are an
   error rather than a race, and the run stops before it renames
   anything. Keeping one of the two silently is how a library
   acquires a systematically wrong abbreviation that nobody can explain
   afterwards.

** When a row has to change the shape of the name

   Some journals are cited with their volume and some are not, and
   which is which is a property of the journal — so it belongs in the
   table rather than in the template. A table may therefore say that
   its value column holds template source rather than literal text:

   #+begin_src toml
     [tables.jcode]
     path   = "journal_titles.tsv"
     key    = ["title", "shorttitle"]
     value  = "code"
     values = "template"
   #+end_src

   Add the column, and leave the ones the file already has alone:

   #+begin_example
     abbreviation  title                                    shorttitle               code
     AA            Amino Acids                              Amino Acids              AA
     ABB-          Archives of Biochemistry and Biophysics  Arch. Biochem. Biophys.  ABB[volume:prefix("-")]
   #+end_example

   Now the one template

   #+begin_example
     [year]-[journal:lookup("jcode")]-[firstpage]
   #+end_example

   names a 2024 paper in Amino Acids on pages 1234–1245 ~2024-AA-1234~,
   and one in Archives of Biochemistry and Biophysics, volume 146, on
   the same pages ~2024-ABB-146-1234~. The template does not know which
   kind of journal it is rendering; the row does.

   Note that the fragment is ~ABB[volume:prefix("-")]~ and not
   ~ABB-[volume]~. A paper in that journal whose record has no volume
   is named ~2024-ABB-1234~, with no dash left dangling where the
   volume would have been — which is the affix filters doing the same
   job for a fragment that they do for a template.

   Values are literal text unless the declaration says otherwise, so a
   value containing ~[~ is data until you ask for it to be a template.
   A fragment is compiled when the table loads, which means a malformed
   one is a configuration error naming the table, the line, the value
   and what is wrong with it, and not a surprise on the four-hundredth
   file. A fragment may not itself contain a ~lookup~: indirection
   stops at one level, so a table cannot send borax round in a circle.

** Misses are reported, not swallowed

   A lookup that finds no row renders the empty string. It is not an
   error, and it does not stop the run — which is what lets an
   alternative supply the fallback:

   #+begin_example
     [journal:lookup("jcode") || journal:abbr]
   #+end_example

   But it is never silent. Every miss is reported once per distinct
   table and value, however many files hit it, as a line of its own:

   #+begin_example
     jcode: no row for "Journal of Unlisted Results"
   #+end_example

   In human output, ~rename~ and ~bib~ count misses in their closing
   summaries. This ~rename~ summary is unchanged:

   #+begin_example
     12 resolved, 12 renamed, 0 skipped, 1 unmatched
   #+end_example

   ~adopt~ has no closing summary count. It prints each miss directly
   above its closing adoption totals. The per-miss report is the point
   of the whole arrangement. It tells you which line to add to your
   file, and it tells you once rather than twelve times.

** Where the file is, and when it is read

   A relative ~path~ is resolved against the directory of the
   configuration file that declared it, not against the directory you
   happen to be standing in. A global ~config.toml~ saying ~path =
   "journal_titles.tsv"~ means the file beside it, and a ~.borax.toml~
   can ship a table next to itself and stay right wherever the run is
   started from. An absolute path is taken as it is written.

   A leading =~= is *not* expanded — not here, and nowhere else in
   borax. Write the path out.

   Tables merge per name, the way templates do, so a ~.borax.toml~ that
   declares one table keeps every table it inherits from the global
   file. ~borax config~ reports ~tables.jcode.path~,
   ~tables.jcode.key~, ~tables.jcode.value~ and ~tables.jcode.values~
   with the origin of each, which is how you answer "which
   abbreviation file am I actually reading".

   Every table is read, parsed and folded before the first file is
   processed. A declared file that cannot be read, a header without a
   column the declaration names, and a key claimed by two different
   values each end the run there, with the reason on stderr, nothing
   renamed and no events on stdout:

   #+begin_example
     tables.jcode: "/srv/lib/journal_titles.tsv" could not be read: No such file or directory (os error 2)
     tables.jcode: the header has no column "abbreviation"
     tables.jcode: line 42: the key "j-chem-soc" is claimed by both "JCS" and "JCHS"
   #+end_example

** Editing a table changes names you have already used

   This is worth saying plainly. A table is an input to every name and
   every citation key rendered through it, so adding a row for a
   journal that used to miss changes what borax calls the papers in it.
   If your ~[citation-keys]~ templates look a table up, it changes the
   keys too — including the ones already typed into a ~\cite{...}~ in a
   document borax has never seen and will never edit.

   That risk is not new; it is the one every citation-key template
   carries. What tables add is that the answer now depends on a file
   you edit, so borax writes down which file it read: the opening event
   of every run names each table by path and by a digest of the
   contents it was read with. When a name and a key disagree six months
   later, the run log says which version of the table produced which.

* Errors are reported before any file is touched

  Templates are compiled when they are loaded — before the first file
  is processed — and an unknown field, an unknown filter, a ~lookup~
  naming a table no configuration declares, a bad regular expression,
  or a syntax error aborts the run then and there. A template is
  configuration, so a broken one is wrong for every file in the batch;
  there is nothing to be gained by discovering that once per file.

  A command compiles the templates it renders from, and no others.
  ~borax rename~ names every file it moves and cites every record it
  admits, so it compiles both tables and either one can stop it.
  ~borax bib~ renders no file name, so it compiles the citation keys
  alone. A ~templates.default~ that will not compile leaves a
  bibliography run alone. You hear about it from ~rename~, where you
  can do something about it.

  ~borax config~ compiles nothing at all. It reports a template as the
  source text your configuration file gave. This keeps it working on a
  configuration that no other command will accept — the situation you
  most want it in.

  The message names the table, the key, and the offending token:

  #+begin_example
    templates.default: unknown filter "lwoer"
    templates.default: unknown field "titel"
    templates.default: template syntax error at byte 6: unclosed '['
    templates.default: unknown table "jcode"
    citation-keys.thesis: unknown field "titel"
  #+end_example

  Rendering itself cannot fail. Once a template compiles, the same
  record and the same configuration always produce the same name.

* Run logs

  Every run can write down what it did, as a /run log/: one JSON object
  per line, in the same schema ~--json~ prints to your terminal. The
  difference is only that the log stays after the process exits.

  Where the log goes depends on where you are working. Inside a
  library — any directory with a ~.borax.toml~ in it, or under one —
  logs are kept in ~.borax/runs/~ beside that file, so a library's
  records travel with the files they are about. Outside a library,
  borax falls back to your platform's state directory (on Linux,
  usually =~/.local/state/borax/v1/runs/=).

  Logs are named so that a listing sorts usefully:

  #+begin_example
    20240419T101500Z-rename-dry.jsonl
    20240419T101642Z-rename-apply.jsonl
  #+end_example

  The timestamp leads, so the newest run sorts last; the ~dry~ or
  ~apply~ suffix trails, so a preview sorts directly above the run that
  applied it. A batch preview has the ~dry~ suffix. A run that may move
  files — an interactive rename or a batch with ~--apply~ — has the
  ~apply~ suffix.

  A preview writes a log by default and you can turn that off with
  ~--no-run-log~. *An interactive rename and a ~rename --apply~ always
  write one, and cannot be talked out of it.* An interactive run is an
  applying run even when you decline every proposal. Its log is created
  and its first event is written before the first question. If borax has
  nowhere to put that log — you are outside a library and your system
  names no state directory — it refuses to ask or move anything.

  Every applying rename records and flushes a move's ~renamed~ event
  before it makes the move. If that event cannot be written, the move is
  not made and the run stops. If the event is written but the filesystem
  then refuses the move, the log contains the ~renamed~ event followed
  by the skip that records the failure. The summary counts that file as
  skipped, not renamed.

  The JSONL stream records the result of each decision, not the question
  that led to it. A ~resolved~ event's ~found~ field is the identifier
  borax looked up, while ~identifier~ remains the identifier under which
  the record is filed. Its ~claims~ field lists every title read from
  the file, in order, with ~from~ set to ~xmp~ or ~info~. The list is
  empty when the content index or library answered without opening the
  file.

  ~resolved.source~ names the services that supplied the record. When
  the content index answers, borax reads those services from the
  record's per-field provenance in this order: Crossref, OpenAlex,
  arXiv, DataCite, PubMed, then a sidecar. It reports ~cache~ only when
  that provenance names none of them; ~cached~ separately records that
  the content index answered. A library answer uses the same provenance
  order and reports ~library~ as its source when the item names no
  service. It always reports ~cached: false~.

  ~resolved.tier~ names the extraction pass that found the identifier.
  It is ~supplied~ when you entered the identifier and ~null~ when the
  content index answered. It is ~library~ when the library item supplied
  the record; ~found~ is then the record's own identifier. A supplied
  re-identification of a tracked file keeps ~tier: supplied~ because the
  operator, not the library, supplied that answer. ~resolved.overrode~
  records a title conflict you accepted. It contains ~field~,
  ~extracted~, ~resolved~, and ~similarity~, the same values carried by
  a skipped conflict, and is ~null~ when you overrode nothing.

  Every ~resolved~ and ~skipped~ event has a ~library~ field. It is
  ~null~ when no library was asked: there is no run library, the file is
  outside it or in an excluded subtree, or resolution ended first with
  a content duplicate. It is also ~null~ on a skip that is not the
  file's resolution verdict, such as ~target-taken~, ~declined~, or
  ~stranding~, because the earlier ~resolved~ event already carries the
  answer.

  Otherwise ~library~ is an object tagged by ~kind~. ~tracked~ carries
  the artifact and item identities, and ~untracked~ carries no further
  evidence. The other kinds explain why the library could not answer:

  - ~unrecognised-content~ :: Records name the path, but none holds the
    file's bytes. It carries those artifact identities.
  - ~ambiguous~ :: Several records at the path hold the bytes. It
    carries their artifact identities.
  - ~no-item~ :: The one matching artifact links to no item. It carries
    the artifact identity.
  - ~dangling-item~ :: The linked item is absent. It carries the
    artifact and item identities.
  - ~unreadable-item~ :: The linked item could not be read from its file
    or the item store could not be listed. It adds the path and reading
    error to the artifact and item identities.
  - ~ambiguous-item~ :: Several item files carry the linked identity. It
    carries the artifact and item identities and those file paths.
  - ~unhashable~ :: Records name the path, but the file could not be
    hashed. It carries their artifact identities.
  - ~unreadable-records~ :: No readable record names the path, but the
    artifact store could not be read completely. It carries whether the
    store was listed and how many record files were unreadable.

  An ~unresolvable~ skip reason contains ~found~, the identifier that
  was looked up, ~tier~, the extraction pass that read it, and
  ~attempts~, the answers from the services.
  The corresponding human-readable line names the identifier too, for
  example ~no source had a record for doi:... (crossref: not found;
  openalex: not found)~.

  ~run-started~ includes the Boolean ~interactive~; an
  interactive run also reports ~applying: true~. A declined proposal is
  a ~skipped~ event with reason ~declined~, and the counts in
  ~run-finished~ include ~unreached~. An already-named file produces an
  ~already-named~ event carrying its path rather than a ~skipped~ event,
  and the counts include ~named~. An interactive run waits until you
  settle a file before it emits that file's outcome, so a supplied
  identifier does not produce a second verdict. Questions are not
  events. The new ~library~ field and the ~library~ values for ~tier~ and
  ~source~ are additions. The event schema version remains 3.

  Schema 3 adds the library events. ~status --identify~ emits one
  ~library-extraction~ event for each surveyed artifact as its
  extraction finishes, in survey order. Its ~path~ is library-relative
  and ~/~ separated. Its ~extraction~ object is tagged by ~kind~:
  ~found~ carries ~identifier~ and ~tier~, which is
  ~embedded-metadata~ or ~text-layer~; the other kinds are
  ~no-text-layer~, ~text-without-identifier~, ~encrypted~, and
  ~unreadable~, which carries ~message~.

  #+begin_src json
    {"schema":3,"event":"library-extraction","path":"sub/a.pdf","extraction":{"kind":"found","identifier":"doi:10.1234/x","tier":"text-layer"}}
  #+end_src

  JSON fields keep their raw values, with any required escaping supplied
  by JSON encoding. Every ~library-extraction~ precedes
  ~library-status~, which stays the last event before ~run-finished~.
  ~run-finished~ counts none of these results. This addition does not
  change the event schema version.

  ~library-status~ carries ~root~, ~artifacts~, ~items~, ~records~,
  ~orphans~, ~nested~, and ~identifiable~. ~library-finding~ carries
  ~path~ and ~finding~, and ~library-validated~ carries ~root~,
  ~findings~, ~orphans~, ~missing~, and ~unlinked~. ~library-repair~
  carries ~id~, ~path~, and ~repair~; ~library-reconciled~ carries
  ~root~, ~records~, ~confirmed~, ~repaired~, ~changed~, ~ambiguous~,
  ~missing~, and ~hashed~.

  An applying rename may emit ~library-admission~ with ~path~ and an
  ~admission~ whose ~kind~ is ~relinked~, ~outside~, or ~unwritten~.
  Adoption emits ~library-adoption~ with ~path~ and an ~adoption~ whose
  ~kind~ is ~recorded~, ~held~, ~unreadable~, or ~unwritten~, followed
  by ~library-adopted~ with ~root~, ~adopted~, and ~orphans~. The
  ~ledger-rebuilt~ event is gone. A ~skipped~ event may now carry the
  reason kind ~stranding~.

** Recovering the names a run replaced

   Renaming is the one thing borax does that leaves no trace in the
   files themselves. A bibliography file can be written again, and an
   artifact record keeps the current library-relative path and hash
   history, but the name a file used to carry is nowhere except the log
   of the run that changed it.

   Each rename appears in the log as one line like this:

   #+begin_example
     {
       "schema": 3,
       "event": "renamed",
       "path": "/papers/reviewed-final.pdf",
       "target": "/papers/smith2024_AwesomePaperBorax.pdf",
       "hash": "sha256-2f0a…"
     }
   #+end_example

   Three fields carry the whole of what happened. ~path~ is where the
   file was before the run, ~target~ is where the run put it, and
   ~hash~ is the content hash it had when it moved. That hash is the
   important one: it identifies the file independently of whatever name
   it now carries, so you can confirm that the file sitting at ~target~
   today is still the one the line describes, and has not been replaced
   by something else since.

   So if a run named files in a way you did not want, you have two ways
   forward, and usually the first is the one you want:

   1. *Correct the template and run ~rename --apply~ again.* borax
      identifies files by their contents, not their names, so it finds
      them wherever the previous run left them — including in
      subdirectories a template created. You do not need to put
      anything back first.
   2. *Read the log*, when what you actually lost was information that
      was in the old names and is not in the metadata: which of three
      copies was the annotated one, which draft was which. Filter the
      log for lines whose ~event~ is ~"renamed"~ and you have the
      complete old-to-new mapping for that run.

   Before moving any file back by hand, hash what is currently at
   ~target~ and check it against the line's ~hash~. If they differ, the
   file there is not the one the run moved — something has replaced it
   since — and moving it would put a stranger under the old name. Check
   also that nothing already occupies ~path~, or you would overwrite
   it.
